WAMR on L4Re — 适配分析

  可行性：高

  L4Re 通过 musl libc 提供了相当完整的 POSIX 接口，而 WAMR 的平台抽象层设计得很干净。核心适配工作量其实不算大。

  需要做的事情，按层次拆解：

  第一层：平台移植层（必须）

  在 core/shared/platform/ 下新建 l4re/ 目录，实现：
  - platform_internal.h — 类型定义，可以直接复用 Linux/POSIX 的 pthread 类型
  - platform_init.c — 初始化，基本是空壳
  - shared_platform.cmake — 构建配置

  因为 L4Re 有 musl 提供的 pthread、mmap、clock_gettime，所以可以直接复用 common/posix/
  下的公共实现（线程、互斥锁、内存映射、时间），只需写少量胶水代码。

  第二层：构建系统适配（必须）

  WAMR 用 CMake，但 L4Re 用 mk/lib.mk。有两个选择：
  1. 在 L4Re 构建系统内构建 — 写 Makefile 手动列出源文件，绕过 CMake
  2. 先用 CMake 生成静态库 — 再在 L4Re 中链接

  选项1更符合你项目的风格，但 WAMR 源文件分散且多（解释器、AOT、libc-builtin 等模块），手写 SRC_C 列表比较繁琐。

  第三层：执行引擎选择（需决策）
  ┌──────────────────────┬────────────┬───────────────────────────────────────────────┐
  │         引擎         │ 适合 L4Re? │                     说明                      │
  ├──────────────────────┼────────────┼───────────────────────────────────────────────┤
  │ 解释器 (interpreter) │ 最简单     │ 不需要 mmap/mprotect 可执行内存，BBB 上也能跑 │
  ├──────────────────────┼────────────┼───────────────────────────────────────────────┤
  │ Fast JIT             │ 可行       │ 需要 mmap + PROT_EXEC，L4Re 支持              │
  ├──────────────────────┼────────────┼───────────────────────────────────────────────┤
  │ AOT                  │ 推荐       │ 离线编译 .wasm → .aot，运行时加载，性能好     │
  ├──────────────────────┼────────────┼───────────────────────────────────────────────┤
  │ LLVM JIT             │ 不建议     │ 依赖太重，不适合微内核环境                    │
  └──────────────────────┴────────────┴───────────────────────────────────────────────┘
  对 BBB (ARM Cortex-A8) 来说，解释器 + AOT 是最实际的组合。

  第四层：WASI 支持（可选但有价值）

  - 文件系统 — L4Re 有 VFS 层，但默认是 noop backend，需要有实际文件系统才有意义
  - 网络 — 需要 lwip 集成
  - 环境变量/命令行参数 — 简单，直接支持

  第五层：产品集成（最后做）

  - 创建 product-mini/platforms/l4re/ 下的最小运行时程序
  - Ned 脚本配置（capability 分配、内存大小等）
  - 可选：作为 L4Re 服务运行，通过 IPC 接收 wasm 模块

  主要难点

  1. 构建系统桥接 — WAMR 的 CMake 和 L4Re 的 mk 系统差异大，手工列源文件是最大的体力活
  2. 可执行内存 — AOT/JIT 需要 mmap + PROT_EXEC，L4Re 的 mmap 实现可能有限制需要测试
  3. 信号处理 — WAMR 的硬件边界检查（HW bound check）依赖 SIGSEGV handler，L4Re 的信号支持有限，建议禁用改用软件检查

  建议实施路径

  1. 先做最小可行版：解释器模式 + builtin libc，不要 WASI、不要 JIT
  2. 验证能跑一个简单 wasm（如 fibonacci）
  3. 再逐步加 AOT、WASI、网络等特性
